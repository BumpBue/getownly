# สคริปต์ตรวจด้วยเบราว์เซอร์จริง

ในโฟลเดอร์นี้มีสองสคริปต์ ทั้งคู่เปิดเบราว์เซอร์จริงเข้าเว็บที่รันอยู่ ไม่ได้จำลองหรือยิง API ตรง

| คำสั่ง | ตรวจอะไร |
|---|---|
| `pnpm test:responsive` | ทุกหน้าของทั้งสามบทบาทที่ความกว้าง 375 / 768 / 1440 px |
| `pnpm test:demo-flow` | เส้นทางสาธิตทั้งเส้น ตั้งแต่ ADMIN สร้างหมวดหมู่ จนถึงตัวเลขในรายงาน |

ทั้งคู่หาเบราว์เซอร์ด้วย `find-browser.mjs` ตัวเดียวกัน (ดูหัวข้อ "เบราว์เซอร์ที่ใช้" ท้ายไฟล์)

## การซ้อมเส้นทางสาธิต (`pnpm test:demo-flow`)

เดินเส้นทางเดียวกับที่จะใช้ตอนนำเสนอ **20 ขั้น** โดยมีผู้ใช้สามคนเปิดเบราว์เซอร์คนละหน้าต่างพร้อมกัน
(ADMIN · ผู้สอน · ผู้เรียน) แล้วสลับกันทำงานตามลำดับจริง

```
0.  ADMIN เข้าระบบ สร้างหมวดหมู่
1a-1f ผู้สอนสมัคร สร้างคอร์ส อัปโหลดปก เพิ่มบทเรียน (วิดีโอ + เอกสาร) สร้างแบบทดสอบ ส่งตรวจ
2a-2b ADMIN อนุมัติคอร์ส และตั้งส่วนแบ่งเป็น 25%
3a-3c ผู้เรียนสมัคร ค้นหาด้วยตัวกรองผู้สอน เติมเงินพร้อมแนบสลิป
4.  ADMIN อนุมัติการเติมเงิน
5a-5b ผู้เรียนซื้อคอร์ส เข้าเรียน และทำแบบทดสอบ
6a-6b ผู้เรียนตั้งคำถาม ผู้สอนตอบ
7a-7b ผู้สอนเปิดรายชื่อผู้เรียน (A9) และตารางส่วนแบ่งรายธุรกรรม (A10)
8.  ADMIN เปิดรายงานสรุป
```

**ขั้น 7b และ 8 ไม่ได้ดูแค่ว่าหน้าเปิดได้ แต่เทียบตัวเลขจริง** — คอร์ส 1,500.00 บาท ส่วนแบ่ง 25%
ต้องได้ 375.00 และ 1,125.00 เท่ากันทั้งในหน้าของผู้สอนและในรายงานของ ADMIN
ถ้าการปัดเศษหรือการอ่าน ledger เพี้ยนเมื่อไร ขั้นนี้จะตกทันที

ภาพหน้าจอทุกขั้นลงที่ `frontend/test/demo-flow-output/` และ**เมื่อขั้นไหนตก จะถ่ายภาพหน้าจอ
ณ วินาทีที่พังไว้ให้ด้วย** (`NN-failure.png`) เพราะข้อความ timeout เพียงอย่างเดียวบอกไม่ได้ว่าหน้าจอเป็นอะไร

### ต้องเตรียมอะไรก่อนรัน

สคริปต์เริ่มจาก**ฐานข้อมูลที่มีแค่ ADMIN คนเดียว** ที่เหลือมันสร้างเองผ่านหน้าเว็บทั้งหมด
จึงต้องล้างข้อมูลเดิมก่อน ไม่งั้นจะติดอีเมล/ชื่อผู้ใช้ซ้ำ

```bash
# ยกทั้งกองขึ้นมาก่อน (ฐานข้อมูล getownly_docker แยกจาก getownly ของ dev)
docker compose --profile full up -d

# ล้างข้อมูลแล้วใส่ ADMIN คนเดียวกลับเข้าไป
docker compose exec api sh -c "cd /app/backend && node_modules/.bin/tsx prisma/bootstrap-admin.ts"

pnpm test:demo-flow
```

รันกับ dev server บนเครื่องก็ได้เหมือนกัน แต่ต้องชี้ฐานข้อมูลให้ถูกและล้างข้อมูลเองก่อน
เปลี่ยนปลายทางด้วย `DEMO_BASE_URL` (ค่าเริ่มต้น `http://localhost:3000`)

ใช้เวลาราว **90 วินาที** ต่อหนึ่งรอบเต็ม

### ข้อควรรู้

- **ไฟล์ที่อัปโหลดเป็นไฟล์จำลองขนาดเล็กที่สุด** — PNG 1x1 · MP4 ที่มีแต่ส่วนหัว · PDF หน้าเปล่า
  พอสำหรับพิสูจน์เส้นทางอัปโหลด แต่ **MP4 ไม่มีภาพให้เล่นจริง** หน้าห้องเรียนจึงขึ้น
  "เล่นวิดีโอไม่สำเร็จ" เป็นเรื่องปกติของไฟล์จำลอง ไม่ใช่ข้อผิดพลาดของระบบ
- สคริปต์**หยุดทันทีที่ขั้นใดขั้นหนึ่งตก** เพราะขั้นถัดไปจะไปอ่านของที่ขั้นก่อนหน้าไม่ได้สร้าง
  แล้วรายงานปัญหาที่สองซึ่งไม่มีอยู่จริง

## วิธีรัน

**ต้องมีสองอย่างรันอยู่ก่อน** เพราะสคริปต์นี้เข้าเว็บจริง ไม่ได้จำลอง

```bash
# เทอร์มินัลที่ 1 — ฐานข้อมูลและบริการเบื้องหลัง
pnpm docker:up

# เทอร์มินัลที่ 2 — ต้องมีข้อมูลตัวอย่างในฐานข้อมูล ไม่งั้นหลายหน้าจะว่างเปล่า
pnpm db:seed
pnpm dev

# เทอร์มินัลที่ 3 — รันการตรวจ
pnpm test:responsive
```

เก็บภาพหน้าจอไว้ดูด้วย (ลงที่ `frontend/test/responsive-output/`):

```bash
pnpm test:responsive -- --screenshots
```

## ⚠️ ห้ามรัน `pnpm build` ขณะที่ `pnpm dev` ทำงานอยู่

ทั้งสองคำสั่งเขียนลงโฟลเดอร์ `frontend/.next` ที่เดียวกัน
ถ้ารันพร้อมกัน แคชจะเสียหายและ**ทุกหน้าจะขึ้น error 500** พร้อมข้อความประมาณ

```
ENOENT ... .next\server\chunks\ssr\[root-of-the-server]__xxxx.js
```

ซึ่งจะทำให้การตรวจรายงานว่าทุกหน้าไม่ผ่าน ทั้งที่หน้าจอไม่ได้มีปัญหาเลย

**วิธีแก้:** หยุด dev server → ลบโฟลเดอร์ `frontend/.next` → เริ่ม `pnpm dev` ใหม่

## เบราว์เซอร์ที่ใช้

สคริปต์ใช้ `playwright-core` ซึ่ง**ไม่ดาวน์โหลดเบราว์เซอร์เอง** แต่จะไปหาเบราว์เซอร์ที่เครื่องมีอยู่แล้ว
ตามลำดับนี้

1. ค่าใน `RESPONSIVE_BROWSER` ถ้ากำหนดไว้
2. Chromium ที่ Playwright เคยดาวน์โหลดไว้ (`%LOCALAPPDATA%\ms-playwright`)
3. Microsoft Edge (มีอยู่แล้วในทุกเครื่อง Windows)
4. Google Chrome
5. `chromium` หรือ `google-chrome` บน Linux

ถ้าหาไม่เจอเลย จะขึ้นข้อความบอกให้ระบุ path เอง:

```bash
RESPONSIVE_BROWSER="C:/Program Files/Google/Chrome/Application/chrome.exe" pnpm test:responsive
```

## เกณฑ์ที่ถือว่าไม่ผ่าน

| รหัส | ความหมาย |
|---|---|
| `OVERFLOW` | หน้ากว้างเกินจอ ต้องเลื่อนซ้ายขวาถึงจะเห็นครบ |
| `OFFSCREEN` | ปุ่มหรือลิงก์อยู่นอกพื้นที่ที่มองเห็น — อาการที่พบบ่อยที่สุดคือคอลัมน์ปุ่มสั่งการของตารางหลุดออกไป |
| `SMALL` | ปุ่มเตี้ยกว่า 36 px ที่จอ 375 px กดด้วยนิ้วยาก |
| `TABLE` | ตารางกว้างเกินจอโดยไม่มีตัวเลื่อนแนวนอนครอบ |

**`OVERFLOW`, `OFFSCREEN` และ `TABLE` ทำให้สคริปต์คืน exit code 1** ทั้งสามอย่างแปลว่ามีปุ่มที่กดไม่ถึงจริงๆ
ส่วน **`SMALL` ขึ้นเป็นคำเตือนแต่ไม่ทำให้ตก** เพราะเป็นเรื่องดุลยพินิจ —
ลิงก์ข้อความในหัวเรื่องย่อมเตี้ยกว่าปุ่มเสมอ ถ้าให้ตกด้วยสคริปต์จะแดงตลอดเวลาจนไม่มีใครสนใจ
แต่ยังพิมพ์ออกมาให้เห็นทุกครั้ง

จึงนำไปต่อกับ CI ได้ทันทีถ้าต้องการ

### สิ่งที่จงใจไม่นับว่าไม่ผ่าน

- ลิงก์ที่อยู่ในประโยค (เช่นลิงก์ในย่อหน้าหรือในเซลล์ตาราง) — เป็นสิ่งที่อ่าน ไม่ใช่ปุ่มที่กด
- ช่อง checkbox และ radio — มี label ของตัวเองให้กดอยู่แล้ว
- ลิงก์ใน header, sidebar และ footer — ซ้ำกันทุกหน้า ถ้ารายงานจะได้ผลเดียวกัน 84 ครั้ง
  (ถ้าส่วนพวกนี้มีปัญหาจริง จะโผล่มาเป็น `OVERFLOW` แทน)

ปรับเกณฑ์และรายการยกเว้นได้ที่ `responsive.config.mjs`
